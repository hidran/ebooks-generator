# Lezione 99. Monolite modulare o microservizi

## Punti chiave

### Che cosa costano i microservizi

- Rilasci e scalabilità indipendenti
- Ogni chiamata passa dalla rete
- Dati divisi: niente transazione unica
- Più pipeline, più monitoraggio

### Criteri per decidere

- Più team che si bloccano a vicenda?
- Carichi molto diversi tra le parti?
- Rilasci con ritmi indipendenti?
- Se no: un solo deploy (KISS)

### Monolite modulare con Spring Modulith


> Percorso: orders, poi catalog (API), poi catalog.internal.

- Modulo: package diretto sotto com.shop
- Package base: API pubblica del modulo
- Sottopackage: dettagli interni
- ApplicationModules.verify() in un test

### Prima e dopo (DIP)

- Prima: OrderService usa InMemoryProductCatalog
- Dopo: OrderService usa l'interfaccia ProductCatalog
- Test di modularità: da rosso a verde
- Non servono: rete, servizi, database separati

`src/main/java/com/shop/orders/OrderService.java`

~~~java
package com.shop.orders;

import com.shop.catalog.Product;
import com.shop.catalog.ProductCatalog;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final ProductCatalog catalog;

    public OrderService(ProductCatalog catalog) {
        this.catalog = catalog;
    }

    public Order place(long productId, int quantity) {
        Product product = catalog.find(productId)
                .orElseThrow(() -> new IllegalArgumentException("Unknown product " + productId));
        return new Order(product.id(), product.name(), quantity, product.priceInCents() * quantity);
    }
}
~~~

`src/main/java/com/shop/catalog/internal/InMemoryProductCatalog.java`

~~~java
package com.shop.catalog.internal;

import com.shop.catalog.Product;
import com.shop.catalog.ProductCatalog;
import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Service;

@Service
public class InMemoryProductCatalog implements ProductCatalog {
    private final Map<Long, Product> products = Map.of(
            1L, new Product(1L, "Keyboard", 4900),
            2L, new Product(2L, "Mouse", 2500),
            3L, new Product(3L, "Monitor", 18900));

    @Override
    public Optional<Product> find(long id) {
        return Optional.ofNullable(products.get(id));
    }
}
~~~

`src/test/java/com/shop/orders/OrderServiceTests.java`

~~~java
package com.shop.orders;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

@SpringBootTest
class OrderServiceTests {
    @Autowired
    OrderService orders;

    @Test
    void computesTheTotalFromTheCatalogPrice() {
        Order order = orders.place(1L, 2);
        assertThat(order.productName()).isEqualTo("Keyboard");
        assertThat(order.totalInCents()).isEqualTo(9800);
    }

    @Test
    void rejectsAnUnknownProduct() {
        assertThatThrownBy(() -> orders.place(99L, 1))
                .isInstanceOf(IllegalArgumentException.class)
                .hasMessage("Unknown product 99");
    }
}
~~~

## Riepilogo

- Microservizi: vantaggi reali, costi reali
- Decidere con criteri: team, carico, rilasci
- Monolite modulare: confini nei package
- verify() rende i confini un test
- Dipendere dall'API pubblica del modulo
